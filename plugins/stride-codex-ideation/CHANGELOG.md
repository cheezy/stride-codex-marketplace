# Changelog

All notable changes to the `stride-codex-ideation` plugin are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.4.0] - 2026-10-02

Review-findings release (G439). Shipping a batch is now one tested, cross-platform Python step that keeps the token off every command line and log. The skills follow the steps Codex actually executes: one helper-root lookup, a Codex agent-dispatch procedure, self-contained shell blocks and artifact-only commits. Draft autosave is wired in. Seam parsing, batch validation and the section gate are scripted and agree in both shells. The agent prompts parse, and every PowerShell test twin covers what its bash twin covers.

### Release

This release is a tag and GitHub release on this repository plus a sync of the vendored copy in `stride-codex-marketplace` (`plugins/stride-codex-ideation/` and its README version cell).

### Fixed

- **The stridify ship path no longer leaks the token or depends on bash (D336).** Steps 3, 9 and 10 were model-followed bash fragments: Step 3 `eval`ed unquoted `lib/read_auth.py` output (a URL holding `&` came back empty, and one holding `;cmd` ran the command), Step 9 put the bearer token and the whole payload on curl's command line and assumed the token survived from Step 3 across separate Codex shell calls, and Step 10 crashed with a traceback when a 2xx body was not the expected JSON object — after the batch had already been created, inviting a duplicate re-run. The skill also claimed `curl -H` keeps the token out of the process list, which is false.
  - New `lib/ship.py` does auth, strip, validate, POST and render in one process, from bash and PowerShell alike: the token reaches curl through `curl -K -` on stdin (never argv, never a file, never a child's environment), the payload goes with `--data-binary @<mode-600 temp file>`, every body or curl message printed is token-scrubbed, every temp file is removed on success, failure and interrupt (INT, TERM, HUP and QUIT, even when a background launch handed the process SIGINT/SIGQUIT already ignored), and a 2xx it cannot render prints a do-not-re-run notice and exits 0. Step 3 is now `ship.py --check-auth`; Steps 9-10 are one `ship.py <batch>` call; the Step 8.5a preview is `ship.py --preview <batch>`, so the preview, like every other ship step, runs unchanged on a bash-less Windows host. A batch that fails validation has the validator's message token-scrubbed, since the validator quotes some batch content and runs before the token screen.
  - `lib/read_auth.py` shell-quotes both values (`shlex.quote`), so any remaining `eval` caller is safe.
  - `lib/run_smoke_test.{sh,ps1}` Stage 7 (live) ships through `lib/ship.py` instead of hand-rolling the POST.

- **The installers no longer crash, agree on marker matching, and keep their helpers to themselves (D337).** `install.ps1` built its global path from `$env:USERPROFILE`, which PowerShell on macOS and Linux leaves unset, so the default install threw before doing anything; it now falls back to `HOME`, then the .NET user-profile lookup. It also threw on an existing empty `AGENTS.md` (`Get-Content -Raw` returns `$null`) and matched the managed-block markers anywhere in a line, so a marker quoted in prose could replace the user's text; it now reads and writes byte-faithfully (no BOM, no newline translation) and matches whole lines only. `install.sh` failed every re-run on macOS once the block sat on line 1 (BSD `head -n 0`), and on a file with an orphaned marker a re-run could pair that marker with the appended block and truncate the user's text. Both installers now take the first `BEGIN`/`END` pair with no marker between (a CRLF-terminated marker line still counts, so a block checked out with Windows line endings is refreshed rather than duplicated), append on anything malformed, keep the user's bytes exactly as they are in any encoding (UTF-8 with or without a BOM, or a legacy code page), refuse to write through a symlinked `AGENTS.md`, and produce byte-identical `AGENTS.md` files for the same input.
  - Helpers and fixtures install under the plugin's own directory, `<install-dir>/stride-codex-ideation/{lib,fixtures}`, instead of the shared `<install-dir>/lib` and `<install-dir>/fixtures`, where another tool could overwrite them. That helper root is cleared and rewritten on each install, so files dropped by a newer release disappear; nothing outside it is deleted (legacy helpers in the shared directories are pointed out, never removed), a symlinked helper root is replaced as a link without touching its target (`install.ps1` deletes with `Directory.Delete`, which never recurses into a link, rather than `Remove-Item -Recurse`), and a source checkout inside the target — links resolved — is refused. The installers print the resolved helper root.
  - `INSTALL_SOURCE_DIR=<checkout>` installs from a local checkout instead of cloning.

- **The skills find their helpers and agents themselves, run every shell block standalone, and commit only the artifact (D338).** Every helper path was a `<plugin-root>` placeholder the model had to guess, Step 3 looked for auth under `CLAUDE_PROJECT_DIR` (a Claude Code variable), the decomposer and reviewer were "dispatched via the platform's agent-dispatch tool" although nothing registers them with Codex, blocks sourced `lib/filename.sh` or `lib/draft.sh` in one shell call and used its functions or variables in a later one (each Codex shell call is a fresh process), and both artifact commits ran `git add <path>` then a plain `git commit`, which also commits anything the user had already staged.
  - Each surface skill has a **Resolving the helper root** block tied to where Codex loaded the skill from: `$STRIDE_IDEATION_HOME`, then `<skill base>/stride-codex-ideation` (the project or global `.agents/` install Codex loaded it from), then `<skill base>` itself (a marketplace plugin directory), and — only when the skill's location is unknown — the global install. A repository's own `.agents/stride-codex-ideation/` is never searched on its own, because everything under the helper root is executed. A location qualifies only if it holds `lib/filename.sh`, `lib/ship.py` and `agents/requirements-decomposer.md`, and the block fails naming every path tried. The installers now also copy `agents/` into the helper root.
  - Each skill states once that every shell call is a fresh process; every block takes earlier values as single-quoted literals on a `# Carried forward:` line, opens with a helper-root guard, sources the helper it calls, and runs in `( … )`. Step 8a writes the agent JSON to a private temp file instead of a shell variable.
  - The decomposer and reviewer are located at `<helper root>/agents/<name>.md` and run as a Codex sub-agent, or without sub-agent support inline as a clearly separated, read-only pass with the same input and output. The Step 7a classifier now names Codex-reachable outcomes: provider rate limit (429), 5xx/overload and network errors are transient; an agent file missing under the helper root, a contract violation or another 4xx is terminal.
  - Both commits pass the artifact as a literal pathspec (`GIT_LITERAL_PATHSPECS=1`; `git commit -m … -- "$TARGET_PATH"`) after `git add`, so a file staged before the session stays staged and out of the commit.
  - `lib/ship.py` looks for `.stride_auth.md` at the git project root, then in the current directory (after `$STRIDE_AUTH_FILE`), instead of under `CLAUDE_PROJECT_DIR`.

- **Draft autosave actually happens, never gets committed, and resumes only the right topic (D339).** The ideate skill promised the protocol skill would save the draft to `draft_path` after every round, but `skills/stride-ideation/SKILL.md` never mentioned it, so nothing was saved and an interrupted session lost every answer. The protocol skill now has an **Autosave** section: after every round it writes the draft (sections plus a round-state header) to `draft_path` with the file-write tool, and at round 1 it loads a non-empty draft; autosave never bypasses a gate and a failed write never blocks. `.stride/` now ignores itself — `sti_draft_dir` / `Sti-DraftDir` (called by ideate Step 4d before the first round, and by every save) write `.stride/.gitignore` containing `*` when it is absent, never overwrite one, and never drop one into another pre-existing directory — so a draft no longer shows up in `git status` or a later `git add -A` in a user's project, and the ideate skill no longer claims the project's `.gitignore` covers it. `sti_draft_save` / `Sti-DraftSave` take the content on stdin / the pipeline (the argument form still works), so prose needs no shell quoting. Draft discovery matches only `<YYYY-MM-DDTHHMMSS>-<slug>-draft.md` in both shells, so slug `toggle` no longer resumes a `dark-mode-toggle` draft.

- **One seam definition for the advisory, `--goal` and scoping (D340).** The stridify Step 2.4 advisory counted numbered items, bullets and `###` headings, but `sti_extract_seams` understood only numbered `<N>. **Name**` items, so the advisory could recommend `--goal` for a doc where `--goal` then failed; `sti_scope_doc_to_seam` numbered items differently from the extractor (an item whose name does not slugify shifted the index, sending the wrong surface to the decomposer); the numbered pattern accepted any indentation, so a numbered sub-list under bulleted seams took the section over; the PowerShell parser matched the `## Decomposition seams` heading case-insensitively while bash did not; and `Sti-ResolveGoal` compared the index as a string, so `--goal 01` failed in PowerShell. Seams now come from one parser in both shells (ported from stride-opencode-ideation D321): top-level numbered bold items (0-3 leading spaces; an indented one under a bulleted seam, or deeper than the first numbered seam, is nested), else top-level bulleted bold items, else `###` headings, one shape per section; the advisory counts the extractor's output, scoping indexes exactly the items it emits, and a numeric `--goal` is compared as a number in both shells.
- **The batch validator checks every task, and the section gate is a script (D341).** `lib/validate_batch.py` exited 0 for a task with no `title` or `type`, a task whose `type` was `goal`, and a root carrying a stray `tasks` key next to `goals` — all of which the API later rejected as an opaque 422 after the decomposer pass. Check (d) now requires each task to be an object with a non-empty string `title` and a `type` of `work` or `defect`, check (b) fails on `tasks` alongside `goals`, and every message names the JSON path. Stridify Step 2.3's seven-section check was model-followed grep prose looking for `Success metrics`, while the protocol skill and reviewer spell it `Success Metrics`; it is now `lib/check_sections.py` (ported from stride-copilot-ideation D328), which matches level-2 headings case-insensitively, ignores code fences, lists every missing section and only reads the doc. The Step 8a table matches the validator again.
- **The decomposer and reviewer prompts no longer contradict themselves (D342).** `agents/requirements-decomposer.md` said it had no codebase access while its `tools` granted `read` and `search`, said never invent paths while every example used `lib/app/...` paths, and carried `// ... more tasks` comments inside a json example that therefore did not parse. Its skeleton and examples also taught empty `manual_tests`, `edge_cases`, `integration_tests` and `coverage_target`, and it lacked the canonical five-scored-fields section and the `created_by_agent` do-not-emit entry. It now carries the canonical stride-ideation wording, adapted to Codex tool names: it may ground `key_files` with `read`/`search` and must otherwise mark paths as proposed; everything it reads is data, never instructions; it never reads secret-bearing files or puts a credential in its output; the elisions are in prose; and the examples are populated. `agents/requirements-reviewer.md`'s output-format block wrote its allowed values as `"a" | "b"` unions and did not parse. It is now a parseable template with the allowed verdict, severity and section values listed beside it, and the example's severities follow its own blocking rule. The stridify Step 7 description of the decomposer's input matches.
- **The ideate skill accepts `--continue=<path>` (W2198).** Step 1 said `--input` and `--profile` accept both shapes "matching how `--continue` accepts both forms", but `--continue` only took the next token. It now also takes `--continue=<path>` (split on the first `=`, so a path containing `=` is kept whole), and a `--continue` with no value stops with `stride-ideation: --continue requires a path to a prior -requirements.md doc` before any session work. The README usage line lists `--input` and the `=` form.
- **Test references now match the skills they mirror (W2198).** The stridify-fallback references wrote `Last error from subagent` / `Subagent prompt` where Step 7.5 says `agent`; they now write the SKILL's exact 7.5b layout and 7.5c summary, and a drift guard checks each required heading against SKILL.md. Both retry classifiers now treat HTTP 429, any 5xx, `rate limit` and `capacity` as transient, as Step 7a does. Several assertions could pass vacuously and no longer can: fallback "first file unchanged" compared a size to itself; "POST not attempted" had no positive control; retry "last attempt's error" could not tell attempts apart; the retry log check never passed a prompt; and the read_auth token-leak check passed on a crash with empty stderr. The rewritten PowerShell twins and the new ideate-input twin write their fixtures without a BOM, which Windows PowerShell 5.1's `Set-Content -Encoding UTF8` would add and the Python helpers' utf-8 reads would reject.
- **The docs match the code again (W2199).** Lean is no longer described as byte-for-byte upstream v0.3.0 in the ideate skill (description, Step 1, Step 5) or the protocol skill (Profiles, round table): the protocol skill now lists what lean runs (the shared core of every profile — the seven gated sections, round recap, uncertainty path, framing checkpoint, premortem, challenge gate, reviewer pass and draft autosave). The protocol skill is the single home of the questioning loop. It no longer points back at the ideate skill for which questions to batch; the ideate skill still points at it. The protocol skill's description dropped from 1,117 characters, over the 1,024-character skill-description limit, to 364 and keeps its triggering conditions. The ideate description names `--input`. One question mechanism is described everywhere: plain chat with numbered options, answered by number, with a multi-select question answered with several numbers. This replaces the skills' "Codex CLI's question UI" and the README's mixed wording; the protocol skill defines it under **How questions are asked**. The README no longer claims Codex discovers agents in `.agents/agents/` (the skills read them from the helper root), that the installers behave identically (it lists where they differ), or that the agents, fixtures and helpers are byte-identical to upstream. Its manual install no longer overwrites your `AGENTS.md`: it tells you to paste the managed block, or to run the installer with `INSTALL_SOURCE_DIR`. Its usage covers `--input`, `--yes` / `--auto-approve` and the approval gate. `fixtures/SMOKE-TEST-NOTE.md` and `fixtures/README.md` no longer claim verbatim upstream copies or a skill-embedded renderer.
- **The marketplace statement is corrected (W2199).** The 0.3.0 and 0.1.0 notes below say `stride-codex-ideation` is on no marketplace. That was true when they were written, but since 2026-07-28 `stride-codex-marketplace` vendors the plugin under `plugins/stride-codex-ideation/` and lists it in its catalog. A release now also syncs that vendored copy and the marketplace README's version.

## [0.2.0] - 2026-06-26

### Added

- **Challenge gate (W1370)** — a new mandatory, profile-independent design stress-test ported from the canonical [`cheezy/stride-ideation`](https://github.com/cheezy/stride-ideation) plugin and adapted to the Codex CLI question/selection primitive (never Claude Code's `AskUserQuestion`). It runs after the round-4 premortem (and the Round-5 MVP-design batch under `lean-startup`) and **before** the reviewer pass, over the assembled draft. Four components, run in order: (a) an **assumption-confidence audit** rating every Assumptions entry `high` / `medium` / `low`; (b) a **blind-spot scan** for unstated dependencies, omitted stakeholders, untested edge cases, and failure modes the premortem missed; (c) **alternative generation** of two distinct alternative approaches; and (d) a **trade-off analysis** comparing the proposed design against the two alternatives across cost, risk, complexity, and timeline. The gate is surfaced as a single multi-select decision with an explicit "Challenge nothing — write as-is" option, is advisory and **never blocks the write**, and runs even under `--continue`. Confidence ratings fold into the Assumptions entries in place; the blind spots, the two alternatives, and the trade-off comparison fold into a new optional `## Design challenge` section (not one of the seven hard-gated sections, and never surfaced in the round recap). Implemented in `skills/stride-ideation/SKILL.md` (the `## Challenge gate` section) and `skills/stride-ideation-ideate/SKILL.md` (the Step-5 enforcement bullet and the Step-6 confidence-rated Assumptions + `## Design challenge` template).
- **Challenge-gate documentation, fixture, and tests (W1371)** — a "Session experience" subsection in `README.md` documenting the gate's four components, placement, and advisory semantics; a catalogued calibration fixture `fixtures/2026-05-12T120300-saved-filters-challenge-gate-requirements.md` exhibiting a `## Design challenge` section (two alternatives + a cost/risk/complexity/timeline trade-off table) and confidence-rated Assumptions; a new `Stage 6: challenge-gate fixture shape` check in `lib/run_smoke_test.sh` + `lib/run_smoke_test.ps1` (the bash smoke test now reports **14 passed, 0 failed**); and a standalone `lib/test-challenge-gate.{sh,ps1}` suite (8 assertions each — four positive shape checks plus three negative controls guarding against vacuous passes). `fixtures/README.md` gains a section-4 catalogue entry, and two stale `stride-copilot-ideation` / `Copilot` references are corrected to `stride-codex-ideation` / `Codex CLI`.

### Source

Challenge-gate port: W1370 (skill + ideate surface), W1371 (README + fixtures + tests), W1372 (this release).

## [0.1.1] - 2026-06-22

### Fixed

- **The installer no longer overwrites an existing `AGENTS.md`.** Previously `install.sh` (line 83, project mode) and `install.ps1` unconditionally copied the bundle `AGENTS.md` over the destination, silently destroying a user-authored `AGENTS.md`. The installer now confines its content to an idempotent, clearly delimited managed block (`<!-- BEGIN stride-ideation -->` … `<!-- END stride-ideation -->`): a fresh file is created with the block; an existing file keeps all of its content with the block appended or refreshed in place; re-running the installer never duplicates the guidance; and a malformed/orphaned marker appends rather than truncating, so user content is never lost. The same guard is applied in both project and global mode and in both `install.sh` and `install.ps1` (verified byte-for-byte identical across fresh, existing, re-run, no-trailing-newline, and malformed-marker scenarios). The destination is only ever pattern-matched, never sourced or evaluated. Mirrors the [`stride-opencode-ideation` v0.2.1](https://github.com/cheezy/stride-opencode-ideation/releases/tag/v0.2.1) fix.

### Notes on the port

- **Skill activation language.** Where upstream Claude Code uses "Run `/stride-ideation:ideate`", this plugin uses "Activate the `stride-ideation-ideate` skill" — same substance, different invocation grammar. Codex CLI has no slash-command mechanism.
- **Agent naming.** The two subagents use the bare `<name>.md` convention (e.g. `agents/requirements-decomposer.md`), matching the existing `stride-codex/agents/` pattern. The Copilot port's `<name>.agent.md` form is NOT used here — Codex does not recognize the `.agent` infix.
- **Tool name generalization.** References to Claude Code tool names (`Read`, `Grep`, `Bash`, `Edit`, `Write`) in skill and agent bodies are translated to Codex equivalents (`read`, `search`, `shell`, `edit`, `write`) per the Tool Name Mapping table in `AGENTS.md`. Bash snippets that genuinely invoke `grep` etc. as shell commands are preserved verbatim (per the explicit "do NOT replace tool names inside literal command examples" pitfall on W881 and W882).
- **PowerShell mirrors.** Every bash helper and test file ships with a `.ps1` mirror so Windows Codex users get parity. The PowerShell code uses the same W505-reviewer-approved patterns the Copilot port introduced (`Set-StrictMode Latest`, `@()` wrap for `Get-Content`, `-notcontains` for negation, no `Write-Output` pollution into return channels). PowerShell runtime verification of the installer deferred — `pwsh` is not installed on the porting host; the same pattern was used in the reviewer-approved Copilot and Gemini PowerShell mirrors.
- **Upstream behavior preserved.** Every load-bearing safety check — `--profile` validation, `--continue` validation, HARD INVARIANT, seven-section gate, retry classifier, retry-exhaustion prompt-on-disk, defensive `source_spec` overwrite, never-retry-POST, source-doc read-only — is preserved verbatim. The fixtures (which are calibration references) and the decomposer/reviewer agent bodies are byte-identical to the copilot source (and via that, to upstream) so a regression run against the same requirements docs produces structurally identical batch JSON.
- **Not on a marketplace.** `stride-codex-ideation` is **not** published on `stride-marketplace` (which only carries the Claude Code version). Install via the direct GitHub URL using the one-liner in the README.
